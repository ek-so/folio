# Notes and properties

## Note page
- `Editor` switches between `MarkdownPreview` (read-only apart from task checkboxes, accordions, links' menus and dragging list items; open accordions stay open across re-renders) and `MarkdownEditor` (highlighted textarea; Enter in a list continues it with the next `-`, number or `- [ ]`, and on an empty item ends it: `continueList`).
- ✏️ opens the editor at the first block on screen (`visibleOffset`); a double tap or double click on text opens it at that word (on empty space under or between the text: at the end of the note) (counted from two clicks, since iPhones send no dblclick). Closing the keyboard (iOS Done, tapping elsewhere, Esc) or ✓ returns to preview. The finishing ✓ follows the ✓ button rules.
- **Links in the preview** are badges (`LinkBadge`, put in place of each `<a>` by `linkSpots`), even mid-sentence: a website's favicon (Google's favicon service; a globe offline or without one), or for the repo what it points to (note, file, folder; grey link-break when missing), then the link's text, a bit softer than the note's (`text-foreground/75`); at most 420px wide or its container's width, a longer text cut in the middle so its end shows (`MiddleCut`); a tap opens it. Its ⋯ (small, 24px, to fit the line), split off by a 1px gap: Copy link address (a repo link as the app's address of its target), Edit link (`LinkModal`: Name and URL; a bare URL stays bare while it has no other name) and Remove (the link and its text, confirmed). Edits go through `onChange` like a checkbox, found by `linkSpans` (lib/markdown.js, tested), and refused with a toast when the note changed there since the dialog opened; a block whose links don't line up with them (raw HTML links) only offers Copy. Links to a heading (#…) and around an image stay plain. A property's description (note page, board cards) shows its links as the same badges, with the same menu (`InlineMarkdown`; Edit link and Remove change the description). Both use `useLinkEdits`.
- **Dates in the text** (`lib/dates.js`) are written in one form, "17 Oct 2026, 14:30" ("17 Oct 2026" without a time). Every date badge (the preview, properties, planner cards and rows, a repeat's end) shows it without the year when it's this year ("17 Oct, 14:30", `dateLabel`); another year's keeps it. The note's text always keeps the year. Recognized: 2026-10-17, 17.10.2026, 17/10/2026 (day first), 17 Oct, 17th of October 2026, Oct 17, 2026, each optionally with a time on the same line (14:30, 2:30pm, 2pm, at 14:30, T14:30). A time on its own (14:30, 9:05, 2:30pm, 2pm, 9 a.m.; minutes have 2 digits, so 3:1 isn't one) is written "14:30". Without am/pm a one-digit hour from 1 to 6 is the afternoon ("2:30" is 14:30; "02:30" and "9:05" are as written). A year has 4 digits (17.10.26 isn't a date); a missing one is the current one. A month starts with a capital letter ("march" is a word), except right after its day ("5 oct"); words like "tomorrow" aren't dates; nothing reaches across a line break or into a file name (2026-10-17.md). Only where the preview shows plain text: never in code (fenced or indented), links or HTML (`withFixedDates`, `textRanges` in lib/markdown.js).
- **Every date in the note is rewritten when the editor closes** (✓ or Done, or leaving the page or view while still editing; even with nothing typed): `useNote`'s `beginEdit` / `endEdit`. Closing the browser tab while editing saves the typing as it is. If formatting fails, the note is saved as typed, with a message. **Properties too:** each value gets its dates written the same way, as text; a list item that gets a comma (a time) moves its list onto `- item` lines (`withValue`), so it stays one value.
- **The preview** shows every date, in any form, as a badge in the line (`DateBadge`, in place of each date spot `<time>`, which keeps what's typed in `data-raw` for list dragging and a double tap): a calendar, then the date, no ⋯; grey, icon too, and small (20px, text-xs) so the line keeps its height. Tapping it opens the one date picker (`DateField`, `DatePopover`, shadcn's `Calendar`), the same whatever is written (a day, a time alone with a clock icon, both): the Calendar, Remove date (red ✕) when there's a day, then + Add time when there's no time, else the time field with a red ✕ (Remove time). A picked day replaces the day, its time kept; a time (saved on Enter or leaving the field) is set or added; taking out the day keeps the time and the reverse. A date in the text can't be emptied: its last part has no Remove (`required`) (`useDateEdits`: the i-th spot is the i-th date of `dateSpans`, and only when it's still what's typed there). A description's dates (note page, board cards) work the same.
- **A date property** (its value one date, or while empty every value the notes nearby have one: `isDateProp`, `valueDate`) shows the same grey badge at the size of the other property badges, calendar icon on the left and no ▾, and opens the same date picker instead of the values list; taking out its last part (or the same day tapped again, without a time) empties it. The planner's Go to a day and a repeat's end date use it `dayOnly`: no time, never emptied.
- **Dragging list items** (bullets, tasks, numbers) in the preview: a ⠿ handle (`ListGrip`), always shown, in the text column before the item's marker (a list that can be dragged indents by its width, 24px, more; App.css) (hold 0.25s on touch to drag, as on the board). An item moves with its sub-items, only among the items of its own list (`@dnd-kit`); a numbered list is numbered again from its first number. Pure logic in lib/markdown.js (tested): `listsIn` finds the items in a list block's markdown (handles only where they match the rendered items in number and first word), `moveListItem` writes the new order, through `onChange` like a checkbox. A block whose lists don't line up with the markdown (a list in a quote) has no handles.
- The preview never scrolls sideways: text wraps; a wide table or code block scrolls inside itself (a table column is at least 7rem wide, `min-width` in `App.css`). A note's `# heading` is plain markdown.
- Images and PDFs open read-only in `FileViewer` (`useBlob`); PDFs use pdf.js (`PdfView`, loaded on first use) and draw only pages near the screen, for iOS memory. `Editor` and `FileViewer` share `FilePage`.

## Properties (front matter)
- Shown on top of the preview in a light grey box (`bg-secondary/50`, 16px padding, 16px under its title) titled Properties (`PropertyBadges` with `title`; a double tap opens the editor at the start of the file; board cards use it bare), in the file's order.
- The `description` (`DESCRIPTION`) is muted text whose markdown links are link badges, opened like the note's own, and whose dates are date badges (`renderInline`); never a badge. Every other value is a badge (no property name, no tooltip). Badges listed before the description show above it, the rest below.
- Each badge has a ▾ and opens a popover to change that property, through `useNote`'s `change` in a note and `setProperty` on a board card (both `withValue`).
- A click, press or touch inside a badge or its popover doesn't reach the note or card (`own`). The editor shows the raw block.
- **A widget's properties** (`valueScope`, e.g. a planner's `date` and `repeat`): on the note's page its `order` comes first (a planner's: description, date, repeat); in the editor their lines (`keyLines`: the key's line and its `- item` lines, in a closed front matter block) are greyed out and typing that would change, add or remove them is refused with a message (`MarkdownEditor` `locked`); and when the text was changed in the editor and lacks one (`required`, also a board's group property), it comes back, empty, as the editor closes (`useNote`), moved into that `order` in the file (`withKeysFirst`).

## Value popover (`ValueChooser`)
- A field to find or add a value, the values the notes next to it have for that key (the note's folder; on a card, and on the page of a note that is a card of any board, the whole board: `valuesOf`, `valueScope`) with a ✓ on the current ones, then a separator and **Edit values**.
- A property with a list toggles values and stays open; a single-value property takes the chosen one (choosing it again empties it) and closes. An empty property shows its name as a badge to fill. Without `onChange` (a card being dragged) badges are plain and empty ones aren't shown.
- An outside click or Esc closes it.

## Values dialog (`ValuesModal`, from Edit values)
- One dialog with every value of the property, a field to add one (it's set on this note, like choosing it; on a single-value property a line under the field says which value it replaces), and on each row a color swatch, a pencil and a red trash.
- **Swatch:** a sub popover on its side with the ten colors (`ColorPicker`); choosing one recolors that value at once, without touching any note.
- **Pencil:** the row becomes a name field with only ✓ / ✕ until you accept or dismiss. Save renames the value, keeping its color, in every note in scope. A name another value has merges them (the row says so), in that value's color. Old names keep their picked colors: colors are repo-wide, and the old name may still be used elsewhere.
- **Trash:** closes the dialog, asks first (`ConfirmModal`, with the number of notes), then empties that value in scope.
- **Scope:** the note's folder, or the whole board for a board's card (on the card and on its page). The same actions for both (`valueActions` in `lib/frontmatter.js`): this note changes through `change`, the others through `editNote` (`renameValue`, unchanged when the name is; `withoutValue`: empty for a single value, out of the list for a list).

## Colors
- Each value has its own badge color within its property, `--tag-0`…`--tag-9` tinted by `--tag-tint` against `--card`, stronger on hover; an empty one is grey.
- Automatic (`valueColors`): a value prefers the color its name hashes to, a taken one gets the next free; up to ten values differ.
- Picked colors are saved by key and value for the whole repo (not per folder) in `.folio/colors.json` (`useTagColors`, `lib/tagColors.js`). A picked color wins over the automatic one, and other values avoid it. An unreadable file is never saved over.
